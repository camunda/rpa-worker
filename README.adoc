= Camunda RPA Worker

The Camunda RPA Runtime is designed to bridge the gap between Robotic Process Automation (RPA) bots and the Camunda
workflow engine, enabling you to seamlessly integrate your task workers with Camunda.

== Getting Started

=== Obtaining the RPA Worker

Downloads and details for container images are available on the  https://github.com/camunda/rpa-worker/releases[Releases]
page.

=== Configuration

The RPA Worker can source its configuration either from a configuration file, or environment variables. The RPA Worker
will look for a file named `rpa-worker.properties` in the current directory.

==== Worker HTTP API security

The script evaluation API executes supplied Robot scripts with the worker's OS
permissions and inherited environment, including any cluster credentials.
The name "sandbox" does not imply process, filesystem, or network isolation.
Only run scripts from trusted authors.

Evaluation requires a separate worker API token. Generate at least 32 random
bytes, for example with `openssl rand -hex 32`, then set
`camunda.rpa.api.token` in your protected worker configuration or
`CAMUNDA_RPA_API_TOKEN` in its environment. Tokens must contain at least 32
letters, digits, underscores, or hyphens. No token is configured by default;
evaluation remains inaccessible until one is supplied.

Enter the same token in Modeler's RPA worker configuration under
*Additional configurations* > *API token*. Clients send
`Authorization: Bearer <token>` with requests. Do not reuse Camunda cluster
credentials. Camunda client authentication protects outbound cluster requests,
not the worker's inbound HTTP API. Protect the worker and Modeler configuration
files and never put tokens in URLs or scripts.

Desktop builds bind to localhost. Requests must also use a trusted Host
authority: `localhost`, `127.0.0.1`, or `[::1]`, with the actual listener port.
For intentional remote use, configure exact additional authorities, including
ports, through `camunda.rpa.api.allowed-hosts`, and protect the connection with
HTTPS and network access controls. Wildcards are not supported. Reverse proxies
must preserve an allowed Host authority; forwarded headers are not an
authentication mechanism. Modeler permits plain HTTP only for loopback workers.

For production workers, disable evaluation with
`camunda.rpa.sandbox.enabled=false`. Container images do this by default.
Disabling evaluation does not disable Python callbacks: each running execution
receives a separate random `RPA_CALLBACK_TOKEN`, which authorizes only its
workspace and associated job and is revoked when execution ends, including on
failure or cancellation. The worker API token cannot authorize callbacks.
Job keys alone cannot authorize BPMN errors. A sandbox execution may use job key
`-1` for stubbed error reporting only; it cannot send a real cluster command.

Read-only requests to `/actuator/health` and its subpaths, including
`/actuator/health/liveness` and `/actuator/health/readiness`, do not require a
token or trusted Host authority. Kubernetes probes can use pod IPs without
custom headers. Health groups must be enabled in the Actuator configuration
when used. API documentation remains readable without a token, subject to Host
validation. Workspace artifact URLs remain read-only capabilities so reports can
be embedded in Modeler; keep these URLs private. They remain readable while the
workspace is retained, independently of callback token revocation.

Upgrade the worker, Python library (`camunda-utils` 1.3.0 or later), bundled
runtime (0.3.0 or later), and Modeler integration together. Older Python
libraries do not send execution credentials and their callbacks are rejected;
there is no unauthenticated compatibility mode. Static runtimes must be rebuilt
with the updated library.

===== Monitoring upgrade configuration

`/actuator/prometheus`, `/actuator/metrics`, and their subpaths require both the
worker API token and an allowed Host authority. Existing scrapers must be
configured before upgrading. Use a stable internal DNS name rather than relying
on changing pod IPs, and include its port in `camunda.rpa.api.allowed-hosts`.
If scraping through a reverse proxy, preserve an allowed authority.

For example, allow `rpa-worker.monitoring.svc:36227` and configure Prometheus:

[source,yaml]
----
scrape_configs:
  - job_name: rpa-worker
    metrics_path: /actuator/prometheus
    authorization:
      type: Bearer
      credentials_file: /etc/prometheus/secrets/rpa-worker-api-token
    static_configs:
      - targets: ['rpa-worker.monitoring.svc:36227']
----

Provision the token file securely with the same value configured on the worker.
The example assumes a trusted internal network; protect remote connections with
HTTPS. Health probes remain unauthenticated but a successful health check does
not establish permission to access metrics or execute scripts.

==== Zeebe

Connecting to a Camunda cluster requires providing the configuration for the Zeebe client. The RPA Worker uses the
https://docs.camunda.io/docs/apis-tools/spring-zeebe-sdk/getting-started/#[Spring Zeebe] client, and so uses the same
https://docs.camunda.io/docs/apis-tools/spring-zeebe-sdk/getting-started/#configuring-the-camunda-8-connection[Configuration Properties].

.Example Camunda local dev configuration
----
camunda.client.enabled=true
camunda.client.mode=selfmanaged
camunda.client.grpc-address=http://zeebe.camunda.local
camunda.client.rest-address=http://zeebe.camunda.local
----

.Example Camunda SaaS configuration
----
camunda.client.enabled=true
camunda.client.mode=saas
camunda.client.auth.client-id=<client id>
camunda.client.auth.client-secret=<client secret>
camunda.client.cloud.cluster-id=<cluster id>
camunda.client.cloud.region=<region>

camunda.rpa.secrets.backend=camunda
----

.Example custom/dev SaaS configuration
----
camunda.client.enabled=true
camunda.client.mode=selfmanaged

camunda.client.cloud.cluster-id=<cluster id>
camunda.client.cloud.region=<region>

camunda.client.auth.token-url=https://login.cloud.dev.ultrawombat.com/oauth/token
camunda.client.auth.method=oidc
camunda.client.auth.client-id=<client id>
camunda.client.auth.client-secret=<client secret>

camunda.client.rest-address=https://${camunda.client.cloud.cluster-id}.${camunda.client.cloud.region}.zeebe.dev.ultrawombat.com
camunda.client.grpc-address=https://${camunda.client.cloud.cluster-id}.${camunda.client.cloud.region}.zeebe.dev.ultrawombat.com
camunda.client.auth.audience=zeebe.dev.ultrawombat.com

camunda.rpa.secrets.backend=camunda
camunda.rpa.secrets.camunda.token-audience=secrets.dev.ultrawombat.com
camunda.rpa.secrets.camunda.secrets-endpoint=https://cluster-api.cloud.dev.ultrawombat.com
----

TIP: When creating an API client in the Camunda Cloud Console, the autogenerated configuration file provided contains
most of the necessary configuration for connecting to production Camunda SaaS stacks.


==== Local-only Working

The Zeebe startup check and subscriptions can be disabled by setting
`camunda.client.enabled` to *false*. 
Although the Zeebe Client itself cannot be disabled and it will still log,
the application will keep running allowing local working and these messages can be ignored.

==== Python

When the RPA Worker sets up its Python environment it will install a default set of dependencies. 

Additional dependencies can be installed by providing a supplementary `requirements.txt` file with the 
`camunda.rpa.python.extra-requirements` property.


.extra-requirements.txt
----
numpy==1.26.4
jmespath
----

.rpa-worker.properties
----
camunda.rpa.python.extra-requirements=extra-requirements.txt
----

If the extra requirements files changes, the RPA Worker will install the new dependencies at the next restart, although
no dependencies will be removed. If the Python environment is deleted then the RPA Worker will recreate it from scratch. 

== Robot Job Execution

=== Robot Runtimes

The RPA Worker supports two runtimes for executing Robotframework. 

==== The Python Runtime

The Python runtime creates a dedicated Virtual Environment using an available Python distribution. 
The Python distribution may already be present on the host, or it may be provisioned automatically by the RPA Worker on 
platforms where this is supported. 

The first time the environment is created the RPA Worker will install the necessary base dependencies into the 
environment. 
It will also install, if configured, any additional user-supplied extra requirements. 
If the base requirements change, such as a new version of the RPA Worker updating these dependencies, or the extra 
requirements are updated, then the RPA Worker will update the environment with the new dependencies automatically. 

As dependencies are fetched from the internet, the Python Runtime requires an internet connection.

==== The Static Runtime

The Static Runtime is a pre-built Python environment which is bundled with the RPA Worker. 
It contains a Python interpreter, as well as all the base dependencies, statically linked together in a single 
executable.
As such, when using the Static Runtime it is not possible to install any extra requirements. 

As the base dependencies are included in the Static Runtime, it does not require an internet connection.


==== Choosing a Runtime

The choice of runtime can be configured via the `camunda.rpa.python-runtime.type` configuration property. 
It supports three values: `auto` (the default), `static`, and `python`. 

When the runtime is set to `auto`, the RPA Worker will run the following checks to see if the Python Runtime is 
supported:

* If there is an existing Python environment created by the RPA Worker then this will be used
* If an internet connection is detected, **AND**:
** There is a local Python distribution at a supported version (>=3.10,<3.12) then this will be used to create a new
Virtual Environment, **OR**
** There is no local Python, but it can be provisioned automatically on the current platform (Windows), then Python 
will be provisioned in this way and used to create a new Virtual Environment

If these conditions are not satisfied then the RPA Worker will fall back to the Static Runtime.

NOTE: The Static Runtime is not supported in the JAR distribution of the RPA Worker

=== Built-in Variables

The RPA Worker makes the following environment variables available to the Robot execution:


|===
|Variable |Description

|`RPA_WORKSPACE_ID`
|The workspace ID of the current job

|`RPA_WORKSPACE`
|The full path to the workspace of the current job

|`RPA_SCRIPT`
|The name of the currently executing script

|`RPA_EXECUTION_KEY`
|The execution key of the currently executing script

|`RPA_CALLBACK_TOKEN`
|A sensitive, execution-scoped bearer token used automatically by the Camunda Python library.
It expires when the execution ends; do not log or persist it.

|`RPA_ZEEBE_JOB_KEY`
|The Zeebe Job Key which triggered the Robot execution

|`RPA_ZEEBE_JOB_TYPE`
|The Zeebe Job type

|`RPA_ZEEBE_BPMN_PROCESS_ID`
|The current BPMN process ID

|`RPA_ZEEBE_PROCESS_INSTANCE_KEY`
|The current process instance key

|===

== Supported Configuration

The RPA Worker will source its configuration from configuration files and/or environment variables.
The precedence order is documented in https://docs.spring.io/spring-boot/reference/features/external-config.html[Spring's Externalized Configuration] documentation.

.Configuration Files
A configuration file can be a Properties or a YAML document. 
It can have the name `application` or `rpa-worker`. 
It can be placed in the working directory of the Worker, or in a directory named `config` therein. 
The following are all valid paths to RPA Worker configuration files:

* `rpa-worker.properties`
* `application.properties`
* `rpa-worker.yaml`
* `application.yaml`
* `config/rpa-worker.properties`
* `config/application.properties`
* etc

.Environment Variables
Preferable for container-based deployments, the RPA Worker can source its configuration from environment variables. 
The name of the environment variables follow https://docs.spring.io/spring-boot/reference/features/external-config.html#features.external-config.typesafe-configuration-properties.relaxed-binding.environment-variables[Spring's Binding Rules],
which can be briefly summarised as:

. Convert the property name to upper-case
. Replace dots with underscores
. Remove hyphens

For example `camunda.rpa.zeebe.worker-tags` would become `CAMUNDA_RPA_ZEEBE_WORKERTAGS`.

Launching a dev container with Zeebe connection details, mapping the Worker's listener port to the host, might look like:
[source,shell]
----
$ docker run --rm -it \
    -p 127.0.0.1:36227:36227 \
    -e CAMUNDA_CLIENT_ENABLED=true \
    -e CAMUNDA_CLIENT_MODE=saas \
    -e CAMUNDA_CLIENT_AUTH_CLIENTID=abc123 \
    -e CAMUNDA_CLIENT_AUTH_CLIENTSECRET=def234 \
    -e CAMUNDA_CLIENT_CLOUD_CLUSTERID=ghi345 \
    -e CAMUNDA_CLIENT_CLOUD_REGION=lpp-1 \
    ghcr.io/camunda/rpa-worker:<version>
----

This production example leaves evaluation disabled. For local Modeler
development, explicitly add `-e CAMUNDA_RPA_SANDBOX_ENABLED=true` and
`-e CAMUNDA_RPA_API_TOKEN` after setting that variable to a random token in your
shell. Configure the same token in Modeler. Do not publish an evaluation-enabled
worker on an unrestricted interface or expose it directly to the internet.

=== Internal / Advanced Configuration by Environment Variable

The RPA Worker's environment variables, except `CAMUNDA_RPA_API_TOKEN`,
`camunda.rpa.api.token`, `SPRING_APPLICATION_JSON`, and `spring.application.json`
(case-insensitive), are
inherited by Python/Robot execution. This does not isolate scripts from the
worker account or its configuration files. Both application JSON variables are excluded
in its entirety because it can contain credentials; scripts must not rely on
inheriting settings from it. Supply tokens through protected configuration and
run only trusted scripts. In addition to user-specific environment variables,
there are two internal variables that may be set:

|===
|*Variable*|*Description*|*Default Value*

|`RPA_BASE_URL`
|The URL for the RPA Worker, which the Python/Robot execution will use to 
communicate back to the RPA Worker
|`http://127.0.0.1:36227`

|`SSL_NO_VERIFY`
|Whether the *Python/Robot* execution will ignore HTTPS certificate errors
when communicating back to the RPA Worker (flag variable)
|_Unset_
|===


== Local Cross-Repository Development

The repository's `Makefile` builds and tests changes across the worker, Python
libraries, frozen runtime, and frontend without publishing dependencies remotely.
Check out compatible branches in this sibling layout:

[source,text]
----
workspace/
  rpa-worker/
  rpa-python-libraries/
  rpa-worker-static-runtime/
  rpa-frontend/
----

The local runtime and native build goals currently support macOS only.
Install Python 3.12, JDK 21 for the runtime build, JDK 25 for the worker,
and Xcode command-line tools. Native compilation uses the Gradle-configured
GraalVM toolchain. Frontend tests additionally require Node.js, npm dependencies
installed in `rpa-frontend`, and Chrome (or `CHROME_BIN` pointing to it).

Run these commands from `rpa-worker`:

[source,shell]
----
make help
make check
make jar
make build
make test
----

`make jar` builds a runnable worker JAR; `make build` builds the native worker
and distribution ZIP. Both build a local `camunda-utils` wheel and frozen
runtime first. Set `PYTHON`, `JAVA21_HOME`, `JAVA25_HOME`, `NATIVE_ARCH`,
`WORKER_VERSION`, or `RUNTIME_VERSION` on the Make command line to override
the defaults.

`make test` runs Python pytest, frontend lint/browser tests/build, runtime
build checks, worker unit/functional tests, and infrastructure E2E tests.
Independent suites continue after a failure, but the command returns nonzero
if any suite fails. Individual goals are `test-python`, `test-frontend`,
`test-runtime`, `test-worker`, and `test-e2e`.
Python test dependencies are installed automatically in an isolated virtual
environment using `rpa-python-libraries/requirements.txt`.

Infrastructure E2E requires a pre-provisioned environment matching
`rpa-worker-e2e-tests/build.gradle` and `.github/workflows/build.yml`, including
the container worker at `rpa-worker.local:36228`, Camunda, Kubernetes test
secrets, and Vault. Export `CAMUNDA_RPA_E2E_PATHTOWORKER` with an absolute path
to a compatible native worker and `CAMUNDA_RPA_API_TOKEN` with the same token
used when provisioning the container. Preserve the harness's `CI`, `E2E`, and
`CAMUNDA_VERSION` environment settings when rerunning tests.
The Makefile reports missing prerequisites; it does not provision infrastructure.
The full harness is designed for a disposable Linux environment, so a complete
`make test` run is not supported on an unconfigured macOS checkout.

Generated dependencies, virtual environments, and Python/runtime reports live
in the ignored `.local-build/` directory. Worker test reports remain under each
module's `build/reports/tests/` directory.
The Gradle helper substitutes the local wheel into generated functional-test
requirements without modifying the source fixture.

IMPORTANT: These artifacts reference absolute local wheel paths and are for
local testing only, not redistribution. Local builds use the sibling
`camunda-utils` source; other Python packages still resolve from package indexes.
Runtime goals clean and rebuild the sibling runtime's build directory.
Do not run concurrent builds or tests against the same checkouts.
